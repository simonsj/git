p5551-fetch-rescan.sh fails on the second repetition (GIT_PERF_REPEAT_COUNT
defaults to 3) unless the remote-tracking reset uses update-ref --no-deref.

The script deletes every refs/remotes ref before each measured fetch. The
first fetch now creates refs/remotes/origin/HEAD as a symref to
refs/remotes/origin/master. The next repetition's update-ref --stdin then
sees both "delete refs/remotes/origin/HEAD" and "delete
refs/remotes/origin/master" in one transaction. Without --no-deref that is
two updates of origin/master, which split_symref_update() rejects:

    fatal: multiple updates for 'refs/remotes/origin/master' (including one
    via symref 'refs/remotes/origin/HEAD') are not allowed

Two commits below: the one that added the perf script, then the one that
made fetch create that symref.

    p5551: add a script to test fetch pack-dir rescans
    
    Since fetch often deals with object-ids we don't have (yet),
    it's an easy mistake for it to use a function like
    parse_object() that gives the correct result (e.g., NULL)
    but does so very slowly (because after failing to find the
    object, we re-scan the pack directory looking for new
    packs).
    
    The regular test suite won't catch this because the end
    result is correct, but we would want to know about
    performance regressions, too. Let's add a test to the
    regression suite.
    
    Note that this uses a synthetic repository that has a large
    number of packs. That's not ideal, as it means we're not
    testing what "normal" users see (in fact, some of these
    problems have existed for ages without anybody noticing
    simply because a rescan on a normal repository just isn't
    that expensive).
    
    So what we're really looking for here is the spike you'd
    notice in a pathological case (a lot of unknown objects
    coming into a repo with a lot of packs). If that's fast,
    then the normal cases should be, too.
    
    Note that the test also makes liberal use of $MODERN_GIT for
    setup; some of these regressions go back a ways, and we
    should be able to use it to find the problems there.

    Signed-off-by: Junio C Hamano <gitster@pobox.com>

======== 3. Is 3f763ddf28 a bug because p5551 then needs --no-deref? ========

Argument under evaluation: 3f763ddf28 is not a bug, because the failure it
exposes is repaired by adding --no-deref to the perf script's update-ref,
rather than by changing fetch.

That argument holds. The 2024 commit does the thing its message describes,
and the flag belongs on the test.

3f763ddf28 makes fetch create refs/remotes/<remote>/HEAD when that symref is
missing, which is what clone already did. The default is
FOLLOW_REMOTE_CREATE. t/t5510-fetch.sh covers it. Nothing in that behavior
is an accidental wrong result. A normal clone has had origin/HEAD pointing
at the remote's default branch for years, and a bulk "delete every
refs/remotes name" without --no-deref would already have died the same way
on that clone.

p5551 only avoided the symref because of its setup order. It clones the
parent before the parent has any commits, so clone does not create
origin/HEAD. Before 3f763ddf28, the later fetch did not create it either.
After that commit, the first measured fetch does. The second repetition
(the default GIT_PERF_REPEAT_COUNT is 3) then puts both the symref and its
target in one update-ref --stdin transaction.

update-ref's rejection is the old, intended rule in split_symref_update().
Without --no-deref, "delete refs/remotes/origin/HEAD" is not a request to
delete that name. It is a request to delete what the symref points at,
refs/remotes/origin/master, plus a reflog-only update of the symref. The
explicit "delete refs/remotes/origin/master" on the next line is a second
update of the same ref, which the transaction refuses. That check exists so
one transaction cannot update a ref twice by naming both a symref and its
target. Fetch did not loosen or break it.

--no-deref is the test saying what it already meant. The comment on the
measured block is "start at the same state for each iteration", and the
pipeline deletes every refname for-each-ref printed. With the flag, HEAD is
deleted as a symref and origin/master is deleted as itself. The other lines
are ordinary refs, so the flag does not change them. The measured command
is still git fetch, including the new remote/HEAD update. Reverting
3f763ddf28, or teaching fetch not to create the symref inside this script,
would throw away the behavior the 2024 change added in order to keep a
reset command that was underspecified.

So the need for this one flag is evidence that the perf script's assumption
went stale, not that fetch started doing the wrong thing. The script is
unchanged since 7893bf1720 in 2017, and t/perf is outside make test, which
is why the stale assumption sat there. 3f763ddf28 is a compatible, tested
change in fetch. The bug, if that word fits, is in the reset.
